Render server spec for API-key live screen viewing

Goal
- Use `apiKey` as the only user identifier.
- Show all currently connected live screens on the website.
- Support one-way live screen viewing only.
- No remote control, no two-way commands.

Core idea
- Each extension connects using its `apiKey`.
- The Render server keeps a list of active screen streams grouped by `apiKey`.
- The dashboard shows every live screen currently connected for that key.
- The server only receives frames/status and publishes them to viewers.

Recommended transport
- Extension -> server: WebSocket for live frame upload.
- Website dashboard -> server: poll HTTP for now.
- Secondary live dashboard socket/SSE is commented out for now.
- If video streaming is too heavy, send JPEG snapshots every 1 to 3 seconds instead of full video.

Identity model
- `apiKey` is the main identity.
- You may still generate an internal `screenId` server-side for bookkeeping, but the client only needs to send `apiKey`.
- If the same `apiKey` connects from multiple browsers/screens, show all of them under that same account.

Routes

1. POST /api/activate
Request JSON:
{
  "key": "bnh..."
}
Response JSON:
{
  "status": "ok",
  "expiry": 1760000000000,
  "type": "monthly"
}

2. POST /api/heartbeat
Request JSON:
{
  "apiKey": "bnh..."
}
Response JSON:
{
  "status": "ok",
  "now": 1760000000000
}
Server behavior:
- Mark the key as active.
- Refresh `lastSeen`.
- If you track multiple screens under one key, refresh the specific live connection tied to that socket/session.

3. WS /ws/live-screen
Purpose:
- Extension pushes live screen frames to the server.

Client first message:
{
  "type": "auth",
  "apiKey": "bnh..."
}

Frame message:
{
  "type": "frame",
  "apiKey": "bnh...",
  "timestamp": 1760000000000,
  "image": "base64-jpeg-frame"
}

Optional status message:
{
  "type": "status",
  "apiKey": "bnh...",
  "timestamp": 1760000000000,
  "state": "streaming"
}

4. GET /api/screens?apiKey=...
Response JSON:
{
  "status": "ok",
  "screens": [
    {
      "screenId": "scr_001",
      "apiKey": "bnh...",
      "lastSeen": 1760000000000,
      "state": "streaming",
      "previewUrl": "/api/screens/scr_001/latest.jpg"
    }
  ]
}

5. GET /api/screens/:screenId/latest.jpg
Purpose:
- Returns the latest uploaded frame for that live screen.

6. Commented out for now: WS /ws/dashboard
Purpose:
- This was the secondary live channel for pushing dashboard updates.
- Leave it disabled for now.

Data model

1. users
- apiKey
- planType
- expiry
- createdAt
- updatedAt

2. live_screens
- screenId
- apiKey
- socketId
- state
- lastSeen
- latestFramePath
- connectedAt

3. screen_frames
- screenId
- timestamp
- framePath

If storage cost matters, only keep the latest frame per screen.

How the dashboard should work

1. User opens website dashboard.
2. Dashboard authenticates with `apiKey`.
3. Dashboard loads `/api/screens?apiKey=...`.
4. Dashboard polls `/api/screens?apiKey=...` every few seconds.
5. Dashboard displays `/api/screens/:screenId/latest.jpg` for each active screen.
6. Extension connects to `/ws/live-screen` and starts sending frames.

Recommended timing
- Heartbeat every 15 to 30 seconds.
- Snapshot frame every 1 to 3 seconds.
- Mark a screen offline if no heartbeat/frame arrives for 45 to 60 seconds.

Important implementation rules

- Do not use one global `currentScreen` or `latestFrame` for all users.
- Keep live screens grouped by `apiKey`.
- Keep frame state per `screenId`.
- On disconnect, remove only that screen, not the whole key.
- If several screens use the same `apiKey`, show all of them.

Recommended Render setup

- Use a WebSocket-capable Node server.
- Store screen metadata in memory only if you run one instance.
- If you may scale to multiple Render instances, move live state to Redis/Postgres/object storage.
- Store latest frames on disk, object storage, or Redis depending on traffic.

Minimal acceptance checklist

- A user with one `apiKey` can open the dashboard and see all live screens tied to that key.
- Two or more screens using the same `apiKey` appear separately.
- Dashboard refreshes by polling and shows new screens without needing a secondary live socket.
- Dashboard stops showing a screen after timeout/disconnect.
- Viewing is one-way only: website can watch but not control the client.
